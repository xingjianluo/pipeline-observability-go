# 流水线可观测性组件（本地可运行）

用本地确定性事件流模拟作业运行数据，计算按**作业 × 数据集 × 时间窗口**维度的
新鲜度（freshness）、处理延迟（latency）、吞吐（throughput）与失败率指标，
并在窗口确认时做阈值告警。所有结论满足：

- 与事件到达顺序无关（乱序、迟到在容忍范围内补入，结果与有序到达一致）；
- 对重复投递幂等（同一事件不会重复计数）；
- 已确认窗口的指标与告警**永久冻结、不回退**；
- 超出迟到容忍的事件**不静默丢弃**：被明确拒绝并记录可区分原因；
- **一条流可同时挂多条阈值规则**（含同维度多档），同一窗口可产出多条互相可区分
  （`RuleID` × 告警维度）的告警；每条规则的持续抑制与恢复互相独立；
- 同一持续故障区间告警只触发一次，恢复（含**空闲空窗恢复点**）后再次发生可重新触发；
- **空闲时间段被补确认为空窗口**：零值指标带 `Idle` 标记，与“有数据但数值为零”区分；
- **已确认窗口保留规模可控**（`Config.Retention`），超容量旧窗口可解释地回收，
  迟到事件不能回写回收区间，回收数量可查；
- 每条告警都携带命中规则 ID 与构成该窗口的原始事件 ID，可由原始事件重放复现判定，
  同批输入下告警产出顺序稳定。

## 目录结构

```
pipeline/
  event.go           事件、摄入结果、拒绝原因
  window.go          滚动窗口聚合、指标、空闲空窗标记
  alert.go           多阈值规则、告警、按“规则×维度”去重抑制/恢复
  engine.go          线程安全引擎：摄入、水位推进、空闲填充、窗口确认与保留回收
  *_test.go          乱序/迟到/重复/并发/多规则/空闲窗口/回收/性能等用例
cmd/demo/            本地确定性事件流演示
```

## 事件语义

`pipeline.Event`：

| 字段 | 含义 |
| --- | --- |
| `EventID` | 事件唯一标识。同一 `(Job, Dataset, EventID)` 视为同一条事件，用于去重。 |
| `Job` / `Dataset` | 作业名与数据集名。指标、水位、告警均按该二元组独立计算，互不污染。 |
| `EventTime` | **业务时间**（事件实际发生时间）。窗口归属以此为准。 |
| `IngestTime` | **摄入时间**（到达观测组件的时间）。为零值时由引擎时钟填充。 |
| `Status` | `success` / `failed`。 |
| `Rows` | 本批次产出行数，计入吞吐；不可为负。 |
| `WatermarkHint` | 可选，告知引擎“该流不会再有早于此时间的事件”，用于推进水位。 |

非法事件（缺字段、未知状态、负行数等）以原因 `invalid_event` 拒绝并记入拒绝台账。

每条输入事件都有明确去向，`Ingest` 返回的 `IngestResult` 三者恰居其一：

- **接受**（`Accepted=true`）；
- **重复**（`Duplicate=true`）：此前已摄入，幂等忽略——即使窗口已确认，
  重复事件仍然识别为重复，而**不是**按迟到拒绝，也不重复计数；
- **拒绝**（`Rejected=true`，`Reason` 区分原因，`Detail` 给出水位与边界等判定依据）：
  - `late_beyond_tolerance`：超出允许迟到范围（窗口仍在保留集合内）；
  - `window_reclaimed`：归属窗口早已确认并因保留容量被回收，迟到事件/重复投递都不能回写；
  - `invalid_event`：非法事件。

被拒绝事件可用 `Engine.RejectedEvents()` 取回，绝不静默丢弃。

## 窗口、水位推进与迟到容忍

- 窗口为**滚动窗口**，长度 `Config.WindowSize`（默认 1 分钟），
  归属规则：`start = EventTime.Truncate(WindowSize)`，区间 `[start, start+size)`。
- 每个 `(Job, Dataset)` 流维护一个**事件时间水位 watermark**，取以下三者最大值：
  1. 已观测到的最大 `EventTime`；
  2. 事件携带的 `WatermarkHint`；
  3. `Engine.AdvanceWatermark(job, t)` 显式推进（作用于该作业下所有数据集）。
- 迟到容忍 `Config.AllowedLateness`：
  - 接受条件：事件不重复，且其归属窗口仍开放，或
    `EventTime >= watermark - AllowedLateness`（容忍范围内的迟到/乱序可补入）；
  - 拒绝条件：`EventTime < watermark - AllowedLateness` 且归属窗口已确认
    （或属于一个本应早已确认的未观测窗口）→ `late_beyond_tolerance`。
- **窗口确认（关闭）**：当 `watermark >= 窗口结束时间 + AllowedLateness` 时，
  窗口在下次摄入/水位推进时被确认。确认时从去重后的事件**一次性**计算指标、
  评估告警，随后状态与数值**冻结**：之后任何迟到事件、重复事件、水位推进都
  不会再改变该窗口（迟到超界者拒绝，重复者幂等忽略）。

> 因为 watermark 会随观测到的最大事件时间自动前进，若希望人为制造“容忍内迟到”，
> 应在更晚事件到达之前先摄入迟到事件，或调大 `AllowedLateness`。

## 空闲窗口语义（无数据 ≠ 零值数据）

真实生产节奏里，某段时间完全没有事件上报与“有事件但数值为零”是两回事：

- 当水位越过某个**首个观测窗口之后**、但此前没有任何事件落入的时间格的确认点时，
  引擎会把它**补确认为空闲空窗口**（`WindowView.Idle = true`），指标全为零值、
  状态为 `closed`，与正常窗口一样参与指标查询与告警区间判断；
- **区分**：窗口里有事件但 `Rows=0`（吞吐观测值为零）时 `Idle = false`；
  完全无事件时 `Idle = true`。据此可区分“零值”与“没有数据”；
- **不捏造历史**：空闲填充只从该流第一个被观测到的窗口开始（容忍内迟到带来
  更早的首个窗口时，填充游标自动回退），流从未观测过的远古时间段不会凭空出现窗口；
- **告警语义**：空闲窗口本身**绝不产生越限告警**（无数据不能凭空报故障），
  但它是一个已确认的**恢复点**：所有挂载规则、所有维度的持续故障区间在此被打断。
  因此一次持续异常不能悄悄跨过一段空闲期继续抑制；空闲之后再次越限会**重新触发**。

## 窗口保留与回收边界

长期运行下窗口只增不减，`Config.Retention` 限定**每个 (Job, Dataset) 流最多保留
的已确认窗口数**（`<=0` 表示不限制；开放中的窗口永远保留，不参与回收）：

- 确认周期每轮先做空闲填充、再确认到期窗口，随后按规则回收**最旧的已确认窗口前缀**，
  直到保留数不超过 `Retention`；
- 回收只影响“可查询的窗口集合”：窗口的指标/告警结论在确认时早已冻结，
  已产出的告警（含窗口指纹与 `EventIDs`）与正在进行的**告警区间状态都不受影响**，
  抑制、恢复、复发跨回收边界仍然正确；
- 回收后：
  - 迟到事件落入已回收窗口 → 明确拒绝为 `window_reclaimed`（不静默丢弃、不回写）；
  - 属于该窗口的原始事件再次投递，同样拒绝为 `window_reclaimed`
    （事件去重集合随窗口一起回收，不能再识别为重复）；
  - `Engine.Window(...)` 查不到、`Engine.Windows(...)` 不返回已回收窗口；
- 可观测性：`Engine.RetentionStats().ReclaimedWindows` 给出跨流累计回收数，
  `Engine.ReclaimedWindows(job, dataset)` 给出单流回收数；
- 性能：窗口按起点有序存储，摄入用二分插入；空闲填充以单调游标推进，
  每个时间格生命周期内至多访问一次（均摊 O(1)）；回收只弹出前缀。
  规则按 `(Job, Dataset)` 建索引，评估只遍历该流挂载的规则，不随规则总数线性扫描。

## 指标定义（窗口确认时一次性计算）

| 指标 | 定义 |
| --- | --- |
| `EventCount` / `SuccessCount` / `FailedCount` | 去重后的事件数及按状态分类计数。 |
| `Rows` | 去重事件行数总和。 |
| `ThroughputPerSec` | `Rows / 窗口秒长`。 |
| `MaxProcessingLatency` | `max(IngestTime - EventTime)`（不为负）。 |
| `FreshnessLag` | 窗口应产出时间 `Window.End` 到**最晚成功事件摄入时间**的滞后；无成功事件时退化为最晚摄入时间；提前产出记 `0`。 |
| `SuccessRate` | `SuccessCount / EventCount`。 |

指标只在窗口确认时由完整去重事件集算出，因此乱序到达与有序到达结果完全相同；
窗口一旦确认数值冻结，天然单调稳定、不回退。重复回放同一批事件到全新引擎，
会得到逐窗口一致的结果。无事件的空闲窗口所有指标为零值并以 `WindowView.Idle=true`
标记，从而与“事件数 >0 但吞吐等观测值恰为零”的数据窗口区分（见“空闲窗口语义”）。

## 告警判定规则（多规则 × 多维度 × 区间独立）

`AlertRule` 按 `(Job, Dataset)` 匹配，零值阈值表示**不启用**该类检查：

| 字段 | 触发条件 | `AlertKind` |
| --- | --- | --- |
| `MaxFreshnessLag > 0` | `FreshnessLag > MaxFreshnessLag` | `freshness_breach` |
| `MaxProcessingLatency > 0` | `MaxProcessingLatency > MaxProcessingLatency` | `latency_breach` |
| `MinThroughputPerSec > 0` | `ThroughputPerSec < MinThroughputPerSec` | `throughput_breach` |
| `MaxFailureRate > 0` | `FailedCount/EventCount > MaxFailureRate` | `failure_rate_breach` |

判定时机与依据：

1. 告警只在**窗口确认时**评估一次（空闲空窗也参与评估，但只产生“恢复”效果），
   依据是冻结后的窗口指标；
2. **多条规则并存**：同一个 `(Job, Dataset)` 可注册任意多条规则
   （含同一维度的两档，如吞吐 `<100/s` 严重档与 `<10/s` 轻微档）。
   `RuleID` 在该流内唯一标识规则，为空时自动分配 `rule-1`、`rule-2`…；
   同一流内重复 `RuleID` 的后注册规则替换前者（评估顺序不变）；
3. **同时命中全部给出**：一个窗口同时踩中多条规则、多个维度时，每条命中都产出
   独立告警，结论以 `(RuleID, AlertKind)` 互相区分（即使两条规则的 `AlertKind`
   相同，也是两条不同告警，各自携带自己的 `Observed/Threshold`）；
4. **区间状态互相独立**：持续抑制/恢复状态按 `(RuleID, AlertKind)` 分别维护。
   一条规则恢复或再次触发不会把其他规则（哪怕同一维度的另一档）的状态带跑偏；
5. **去重抑制**：同一 `(RuleID, AlertKind)` 在连续确认窗口中持续越限，
   只在首次越限窗口触发一条告警，后续窗口抑制；
6. **恢复后重新触发**：任一确认窗口（含空闲空窗）不再越限即视为恢复，
   清除该 `(RuleID, AlertKind)` 的持续故障区间；之后再次越限会重新触发；
7. **顺序稳定、可复现**：同一批输入下，告警按“规则注册顺序、规则内固定维度顺序
   （新鲜度→延迟→吞吐→失败率）”产出。`Reason` 包含规则 ID、窗口、指标观测值、
   阈值与触发条件，`EventIDs` 包含参与该窗口计算的全部去重事件 ID——
   据此可从原始事件重放窗口并复算出 `Observed`，完整复现判定。

告警通过 `Engine.Alerts(job, dataset)` 读取（按触发顺序返回副本）。

## 并发模型

引擎内部以单一互斥锁串行化所有状态变更，摄入/推进/查询方法均可并发调用。
`Config.Now` 可注入确定性时钟，便于测试与本地演示复现。

## 测试覆盖

- 乱序事件在容忍范围内补入，指标与有序到达一致；
- 迟到事件：容忍范围内接受、超范围拒绝（`late_beyond_tolerance`）且已确认窗口不被改写；
- 重复投递：窗口开放/确认后的重复均幂等，拒绝台账不包含重复事件；
- 非法事件分类拒绝；
- 指标在不同到达顺序下一致、确认后冻结不回退、整批重放一致；
- 作业/数据集隔离（含水位互不影响）；
- 并发摄入 + 重复投递的去重正确性（`-race`）；
- 告警：持续区间只触发一次、恢复后重新触发、四种维度可区分、由原始事件可复现；
- **多规则**：同一窗口多规则（含同维度两档）同时命中、结论以 `(RuleID, Kind)`
  可区分、顺序稳定可重放；规则之间持续抑制与恢复互不干扰；
- **空闲窗口**：空闲时段补确认为零值空窗口（`Idle`，与有数据零值区分）、
  空闲空窗打断持续故障区间后复发重新触发、空闲本身不造告警、不捏造首个观测窗之前的历史；
- **回收**：超容量旧窗口回收且计数可查；回收后迟到事件/重复投递以
  `window_reclaimed` 拒绝、不回写；进行中的告警区间与恢复/复发判断不受影响；
  已产出告警的证据（窗口指纹、事件 ID）保持完整；
- **性能**：3000 窗口 × 40 规则的摄入在固定预算内完成的护栏用例，
  以及多规则多窗口摄入基准 `BenchmarkIngestScalesWithRulesAndWindows`。

所有断言失败时会打印输入事件列表与判定依据（指标、水位、拒绝/告警详情）。
